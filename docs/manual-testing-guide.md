## 0. Execution rules and prerequisites

### 0.1 Safety, evidence, and result states

- **READ-ONLY** means navigation, searching, inspecting existing data, opening/canceling dialogs, or saving a private PDF. It does not authorize payment, attendance, teaching submission, CMS publication, status changes, or fixture resets.
- **LOCAL-ONLY** cases require an explicitly approved disposable local environment. Choose a unique `RUN` tag such as `QA-20261028-AB` and label every new student, teacher, program, shift, draft, and note with it. Use fictitious data only. Do not send WhatsApp messages, transfer money, call telephone numbers, or publish real family data.
- `npm run seed:local` **clears operational data and recreates demo teacher accounts** before inserting fixtures. Running it requires separate explicit approval and a verified private backup. This document is not reset authorization. Never use `supabase db reset` as a casual prerequisite: it also affects schema/master-data bootstrap and is not the same operation.
- Final teaching submission, payroll closure/payment, draft activation, and enrollment/class removal are consequential even locally. Payroll period changes affect the **whole selected period**, not only the RUN teacher. Do these last, with explicit approval; do not manually unsubmit cards, rewrite snapshots, or delete accounting rows to clean up.
- Restore original CMS values, master statuses, assignments, and draft activation through supported UI actions. Retain inactive RUN records when no safe delete workflow exists. An approved backup restore or approved local reseed is an environment-level cleanup, not an implied step after every case.
- Results: `NOT_RUN` by default; `PASS` only after every expected result is observed; `FAIL` for a mismatch; `BLOCKED` for unavailable data, permissions, hardware, network, or required tooling; `NOT_APPLICABLE` only with a recorded reason. Source inspection and automated tests do not turn a manual case into PASS.
- Attach sanitized screenshots, URLs without tokens, before/after record counts, private PDF references, and relevant error evidence. Never attach passwords, service-role keys, JWTs, cookies, credential manifests, raw authentication dumps, or real personal data. A toast alone is not persistence proof: reload/read back the relevant state.

### 0.2 Environment and accounts

1. Record `git branch --show-current` and `git rev-parse --short HEAD`. Use the approved checkout; do not merge or switch branches automatically while executing a run.
2. Use the existing registered development server at `http://localhost:3000`; if absent, check the workstation port registry before `npm run dev`. Do not silently start another server on an incremented port. `./init.sh` validates lint/tests/build, **not** manual-case completion.
3. Confirm local Supabase API and database routing before any write/reset. The standard local endpoints are API `127.0.0.1:54321` and PostgreSQL `127.0.0.1:54322/postgres`. Shell environment overrides can supersede `.env.local`; do not assume the file alone determines the target. Do not paste secret-bearing environment/status output into a report.
4. Use the ignored, private `supabase/seed-credentials.local.json` as the source of local login credentials. Default seeded identities are admin `admin@uzmacourse.com`, active teachers `guru.demo.01@uzmacourse.test`, `guru.demo.02@uzmacourse.test`, multi-branch teacher `guru.demo.03@uzmacourse.test`, and active teachers 06/07. Guru 04/05 are intentionally inactive fixtures. Environment overrides can change credentials; the manifest wins. Do not reuse historical teacher-account examples or production credentials.
5. Use separate browser profiles/incognito contexts for admin, teacher A, teacher B, and guest, or explicitly sign out between roles. Tabs sharing one profile also share authentication. Use only disposable QA accounts for password/logout tests that could invalidate sessions.
6. Set the test device timezone to `Asia/Jakarta` for shift presentation; record the actual timezone. `D` means today's WIB date; choose past session dates matching the class weekday. `M` means a chosen calendar payroll month; choose non-duplicate, not-yet-closed months for mutating tests. Do not move system/database clocks to manufacture dates.
7. For GPS, installation, notifications, and service-worker cases use a supported secure test origin. A physical phone opening plain HTTP on a LAN address is not equivalent to localhost. Serwist is disabled by `next.config.ts` during `npm run dev`; cold offline reload/install/cache checks need an approved production-mode test server and an active worker for that origin. A loaded dev attendance page can still exercise its JavaScript/IndexedDB queue without proving offline application boot.
8. Use a clean disposable browser profile for offline tests. Do not clear another teacher's real unsynced IndexedDB queue. Database reseeding replaces teacher IDs but does not clear browser queues; keep that distinction in the run record.

If source output still uses `DM-*`, block corrected-seed cases and obtain an approved revision containing the fix; do not rewrite database numbers manually. A previously corrected database does not prove that the checked-out seeder is corrected, and a corrected source file does not prove that existing rows were reseeded.

For a newly generated standard dataset, expected operational counts are 7 classes, 12 placements, 27 invoices, 6 payments and 3 payroll periods (open/closed/paid). Later manual mutations invalidate those baseline counts. Preserve the environment's existing branch/program/variant/CMS baseline; do not assume their counts must equal another workstation's counts.

A local DB operator may use **SELECT-only** observations where UI does not expose a field. Current student list/detail pages do not show NIS; billing rows/receipts/recap and teaching-card rosters can show it when corresponding records exist. A new student without an invoice will not appear in the SPP recap merely because registration succeeded.

For API/operator cases, use an approved private REST client against the local API with its publishable/anon key plus the **actual tested role's** Bearer session token. Never use a service-role key to test RLS. Replace IDs with existing records and verify that a positive authorized control can read them. RLS may return `200` with an empty array; judge unauthorized data exposure, not one fixed status code. Supabase REST uses `/rest/v1/<table>` and `/rest/v1/rpc/<function>`. Obtain tokens privately through the supported login flow. Server Actions are not global browser-console functions: do not type a function name such as `recordPaymentAction(...)` and call that a manual security test. A qualified tester may replay an already captured local request with its actual action identifier/session; never invent those identifiers or include them in public evidence.

### 0.4 Controlled data and execution order

- Use existing **coded** local branches A = Sumokembangsri and B = Junwangi for student/scheduling tests, or separately provisioned approved branches with known distinct codes. The branch UI does not expose a branch-code field; a newly created custom branch can share a fallback NIS prefix. Branch-creation tests are independent and must not silently become NIS setup.
- Create dedicated RUN programs/variants, a RUN teacher assigned to A/B and those programs, and RUN students where mutations are approved. Choose valid unique program initials separately from the longer RUN display tag. For basic board tests use a 30-minute variant, frequency 2/week, capacity 2, SPP 200000 and teaching fee 15000, plus a 15:00–17:00 QA shift. Keep a second variant/program for mismatch tests.
- Seeded teaching cards are mostly already submitted. Do not expect them to be editable. Use an owned QA class/date for draft/submit tests and a class scheduled **today** for attendance. A teacher with no active class today correctly sees “Hari Ini Libur”.
- Snapshot the current active draft per branch before activation tests. After board activation tests, restore the intended approved QA working draft before teaching/attendance cases; activating another draft archives the previous one in that branch.
- Recommended order: read-only smoke → RUN fixture setup → Master Data → board → editable teaching cards → attendance/offline → billing → irreversible payroll closure/payment → CMS with restoration → guides/security/responsive checks. Restore approved local state at the end; never apply this sequence to production.

## Master Data: branches, shifts, programs, teachers, and students

### Local setup and safety

All mutations below are **LOCAL-ONLY**, performed as an administrator against an explicitly identified disposable local database. Choose a unique tester-defined `RUN` tag (for example, `qa-20261028-ab`); replace `RUN` in names, IDs, notes, and dummy email addresses. Use no real family details, phone numbers, credentials, or bank accounts. Record original values before toggling existing QA fixtures. These are procedures, not claims of execution. Reload or reopen the edit page after every successful save to distinguish persistence from optimistic rendering.

Use the existing coded local branches A/B defined in §0.4 for student and scheduling work. TC-BRN-01 creates an independent branch fixture; it is not NIS setup because branch code is not exposed in that UI. Prepare dedicated RUN programs P/Q, an active RUN teacher assigned to A/B and the required programs, and RUN students. Use the 30-minute/frequency-2/capacity-2 variant and QA shift values from §0.4. Removing a program enrollment, variant, placement, or class is a data mutation: use only disposable local records with explicit approval; do not remove referenced operational data.

## Execution record and bug report

The procedure tables above intentionally have no prefilled PASS column. Create a separate private run record for the approved environment. Record every selected case explicitly; unselected cases remain NOT_RUN. A source review, a green automated suite, or a screenshot count is not a completed manual regression.

Run header: RUN tag; tester; branch and full commit; local/approved origin; API/DB target; WIB date/time; browser/OS/version; viewport and real/emulated input; fixture/backup baseline; approved mutation scope.

| Case ID | Status | Actual observation | Private evidence reference | Revision / device / WIB time | State restored / follow-up |
| --- | --- | --- | --- | --- | --- |

Use the status vocabulary in §0.1. If a prerequisite is missing, record exactly which fixture, role, device, network condition or approval is missing. Do not turn an unavailable step into PASS by narrowing its expected outcome.

A bug report must contain the case ID, severity (blocking/major/minor), environment and revision, minimal reproducible steps using RUN data, expected versus actual state, sanitized evidence, and whether the issue is reproducible after a normal reload. Keep secrets and full family records out of attachments. A confirmed mismatch remains FAIL until the application is corrected and that case is rerun; changing this guide's wording is not a product fix.

Important current distinctions:

- Student list/detail do not expose NIS, and branch creation does not expose the branch code. Use coded existing branches and the approved read-only observer for normal-registration NIS tests. Do not promise collision-free concurrent allocation or a permanently fixed five-character width.
- Student enrollment status is not selected into the board's current sidebar data. A non-active enrollment may still look selectable while server placement rejects it. Check rejection/persistence, not a nonexistent guarantee that the row is hidden.
- Teaching-card rendering is based on the current class roster. A correct historical date and a Submitted badge alone do not certify complete historical-roster retention after later placement changes; treat that as a separate regression question rather than assuming a full roster snapshot UI.
- All-status billing totals currently sum returned invoice totals, including cancelled rows. Distinguish displayed tally consistency, unpaid pupil count, and an independent accounting review. Discount snapshots are not recomputed by changing payment date; minimum teacher guarantee is metadata, not automatic pay.
- Invoice RLS currently allows primary-branch reads for a teacher even though the admin billing page is guarded. Do not equate UI hiding with universal API denial. Teacher payroll entries/lines/adjustments have own-teacher predicates.
- Recap PDF and official receipt are different print surfaces. Both components now use body-level portaling with scoped `@media print` isolation to exclude the portal shell and backdrop from native A4 prints. Retain independent verification for each surface.
- CMS list edits are draft state until save, but save publishes to the shared local landing page. Some required HTML inputs unmount when their list item is collapsed; do not infer universal server validation. Media normalization is not an all-field sanitization/security guarantee.
- Public landing may display built-in defaults on missing/failed CMS reads. Use a unique saved RUN value plus editor reload and public readback to establish persistence. Footer contact text, constant-based WhatsApp targets and marketing locations are distinct from Master Data authority.
- Guide printing covers the selected article; its static public screenshot assets are illustrations, not confidential role-protected data. Original-size guide images scroll; the public gallery's transform-based zoom/drag is a different interaction.
- Only attendance is queued offline. Development mode disables Serwist; OS install/notification/print/GPS behavior requires actual supported platform evidence. A viewport screenshot is not physical-device or screen-reader proof.
